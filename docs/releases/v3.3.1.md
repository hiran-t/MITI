# MITI v3.3.1 — `pixi run remove` and clearer connection help

## `pixi run remove`

One command deletes everything MITI's setup generated, on Linux, macOS and Windows:

```bash
pixi run remove
```

It removes `.next`, `node_modules`, `coverage`, the robot message build in `ros/overlay` (`build`, `install`, `log`) and the pixi environments. Source code, `.env` and the message sources in `ros/overlay/src` stay. `pixi run miti` installs and builds everything again.

## When MITI cannot reach foxglove_bridge

The notice at the top now names the address MITI tried and what to do:

> No foxglove_bridge at `ws://<host>:8765`. Start it on the robot and enter the robot's address with the gear in the status bar, or run `pixi run -e humble miti-bridge` (or `-e jazzy`) to run one beside MITI.

`pixi run miti` serves MITI only; with no bridge on the robot or beside MITI it cannot connect. MITI reconnects by itself as soon as a bridge starts.

Checked in Chrome with a fresh profile, from `localhost` and from another address on the network: `pixi run -e jazzy miti-bridge`, `pixi run miti` with a bridge started later, `docker compose up -d` with a bridge on the host, and `docker compose --profile bridge up -d` all connect.

## Windows notes

- **Bridge fails with `LoadLibrary error: 4551`**: Windows blocked an unsigned library pixi downloaded (Smart App Control or an App Control policy). The deployment guide shows how to confirm it and the options: turn Smart App Control off, ask IT to allow the folder, or run the bridge in WSL 2 or on the robot.
- **Keep MITI out of OneDrive**: put the folder somewhere like `C:\MITI`; pixi installs thousands of files that OneDrive would try to upload.

Details: [docs/DEPLOYMENT.md#windows](https://github.com/hiran-t/MITI/blob/main/docs/DEPLOYMENT.md#windows).
