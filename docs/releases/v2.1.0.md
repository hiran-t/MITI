# MITI v2.1.0 — foxglove_bridge and a Foxglove-style 3D Scene

MITI 2.1 connects to robots through foxglove_bridge, rebuilds the 3D Scene settings after Foxglove's 3D panel, loads robot models with their meshes straight from the robot, and keeps cameras and the 3D scene in step with the robot.

## Breaking changes

- **MITI now connects to [foxglove_bridge](https://github.com/foxglove/foxglove-sdk) instead of rosbridge_server.** Run `ros2 launch foxglove_bridge foxglove_bridge_launch.xml` on the robot (default `ws://<robot>:8765`). A rosbridge address saved in the browser is carried over to the same host on port 8765.
- `NEXT_PUBLIC_ROSBRIDGE_URL` is renamed to `NEXT_PUBLIC_BRIDGE_URL`.
- 3D Scene settings use a new format. Layouts saved by MITI 2.0 are converted automatically.

## Connection

- Foxglove WebSocket protocol client (`foxglove.sdk.v1`, falling back to `foxglove.websocket.v1`) with CDR decoding from the schemas the bridge advertises.
- The topic list updates live; subscriptions survive reconnects and node restarts.
- **Streaming** in Connection Settings: _Synchronized_ (default) keeps every topic on one connection, as Foxglove does, so cameras, TF and the scene show the same moment; _Prioritize robot motion_ gives images, point clouds and maps connections of their own for slow links.
- Parameters, services and publishing go through the bridge.

## 3D Scene

- Settings grouped like Foxglove's 3D panel: Frame, Scene, View, Transforms, Topics, Custom layers and Publish.
- Topics lists every topic the scene can draw, with visibility toggles; the robot description is shown automatically.
- Robot models follow TF per link, with joint states for links without TF. URDF custom layers load from a URL, a file path, a node parameter or a topic.
- `package://` and `file://` meshes are fetched through the bridge (as in Foxglove), four at a time, retried on timeout and cached in the browser. Without bridge assets, MITI's server serves them from the local ROS workspace (`/api/package`, `MITI_PACKAGE_PATH`).
- Fixed and display frames with follow modes, a View that tracks the camera both ways, grid layers, render stats, and click-to-publish points, poses and pose estimates.
- Data is placed with TF at its own timestamp by default, with a longer TF history (30 s / 3,000 samples per frame), and the scene updates with every TF message.
- Topic fields commit on Enter or blur, validate ROS names, and warn when a topic's type does not match its layer, with a one-click fix.

## Cameras

- Frames are drawn straight onto a canvas (no PNG re-encoding), including `CompressedImage`, padded rows and big-endian data.
- Every frame is shown by default; an optional Max FPS limits decoding and drawing only.
- The status bar shows received frame rate, frame size and, when the image is stamped on the robot's clock, how far it trails the robot.

## Fixes

- The topic list loads after connecting, and changing the bridge address no longer leaves a stale connection.
- Service call ids no longer collide; occupancy grids and point clouds decode correctly from CDR.
- The topic inspector summarizes large fields instead of freezing on images and point clouds.

## Validation

- Type checking, lint, production build and 66 tests pass.
- Verified against a Unitree G1 in Isaac Sim (ROS 2 Jazzy, foxglove-bridge 3.4.3) over Tailscale: robot model with meshes from the bridge, live TF, lidar and costmaps, cameras at the rate the robot publishes, publishing via a local bridge fixture.

## Known limits

- foxglove_bridge cannot throttle per client: raw camera images can saturate slow links. Prefer compressed image topics there.
- `compressedDepth` images, `CompressedVideo`, and costmap updates (`OccupancyGridUpdate`) are not rendered yet.
- COLLADA textures referenced by meshes fetched through the bridge are not resolved.
- Connection settings are stored per browser.
