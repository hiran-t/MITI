# MITI v3.4.0 — Ports that move out of the way

`pixi run miti` and `pixi run -e <distro> miti-bridge` no longer stop when a port is taken. They pick free ports, and MITI follows the bridge to whichever port it ends up on, so the browser connects without any setting.

## What happens when a port is taken

| Situation                                                                         | What MITI does                                                                       |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Port 3000 is taken                                                                | MITI serves on the next free port (3001, 3002, …)                                    |
| A foxglove_bridge already listens on 8765                                         | `miti-bridge` uses it instead of starting another one                                |
| Another program holds 8765 (for example `svchost` forwarding the port on Windows) | The bridge starts on the next free port (8766, …) and the message names that program |
| `pixi run miti` and a bridge already runs on this machine                         | MITI finds it, on 8765 or the ports after it                                         |

The output starts with the addresses to open:

```
Port 3000 is in use; MITI uses 3001.
Port 8765 is used by another program; foxglove_bridge uses 8766.
MITI: http://localhost:3001  (other computers: http://192.168.10.198:3001)
foxglove_bridge: ws://<this machine>:8766
```

Ctrl+C stops MITI and the bridge it started; a bridge that was already running keeps running.

## Under the hood

- **One launcher for every platform**: `scripts/start-miti.mjs` (Node.js) replaces `ros/miti-with-bridge.sh` and `.ps1`, so Linux, macOS and Windows behave the same.
- **MITI reads the bridge port at run time**: the server passes `MITI_BRIDGE_PORT` to the page on each request. The launcher sets it, and Docker Compose sets it from `BRIDGE_PORT`, so changing the bridge port no longer needs a rebuild.
- **`pixi run bridge`** (bash and PowerShell) reports a foxglove_bridge already on its port instead of starting a second one, and otherwise moves to the next free port, naming the program that holds it. On Windows, for `svchost` it suggests checking `netsh interface portproxy`.

## Checked

In Chrome with a fresh profile, from `localhost` and from another address on the network: both ports taken by other programs (MITI on 3001, bridge on 8766, connected); an existing bridge reused, and left running after Ctrl+C; `pixi run miti` finding a bridge on 8766; Ctrl+C stopping both; a failing bridge stopping MITI; Docker Compose with `BRIDGE_PORT=8799`. The PowerShell port logic was checked with PowerShell 7; Windows itself has not been run yet.
